# Agentic Query Planning

Design plan for evolving vibeQL from one-shot LLM SQL generation into an agentic query planner with tool use, streaming progress, and data-safety guardrails.

## Goal

The current flow asks an LLM to generate SQL directly from a user prompt and schema context. The target flow is an agent/tool chain that can inspect safe database metadata before producing the final SQL.

Primary use case:

1. User asks an ambiguous question, for example "tampilkan customer perempuan".
2. The schema has a likely column such as `gender`, `sex`, `jenis_kelamin`, or `jk`, but the valid values are unknown.
3. The agent determines that the column value mapping is ambiguous.
4. The agent safely checks distinct values for that column, for example `L`, `P`, `male`, `female`, `wanita`, `pria`, `M`, `F`.
5. The agent uses those values to produce a correct final SQL query.
6. The UI streams the agent's visible reasoning/progress to the user without exposing hidden chain-of-thought or unsafe data.

## Non-Goals

- Do not expose private chain-of-thought. Show concise, user-facing progress summaries instead.
- Do not let the AI freely query row-level data.
- Do not send PII values or raw result rows to the LLM.
- Do not auto-run mutating queries.
- Do not replace existing mutation and DDL confirmation guardrails.

## Proposed UX

The query result area should show a streaming "agent activity" timeline before the final SQL appears.

Example visible stream:

```text
Understanding request...
Need to resolve possible gender values in column customers.jenis_kelamin.
Checking safe distinct values for customers.jenis_kelamin.
Found non-sensitive category values: L, P.
Mapped "perempuan" to P.
Generated SQL.
```

This is not raw model reasoning. It is a controlled trace assembled from agent steps, tool calls, and short model-authored summaries.

The final UI should still preserve existing product invariants:

- Generated SQL is always visible.
- Query results are visible after execution.
- Mutations still require preview and explicit commit.
- DDL still requires typed `CONFIRM`.

## Agent Loop

Recommended first version: bounded planner-executor loop.

1. Build a planning prompt from user prompt, schema summary, selected DB dialect, current schema, and safety policy.
2. Ask the model to return structured JSON for the next action, not raw SQL only.
3. Supported actions:
   - `final_sql`: return SQL and query type.
   - `inspect_distinct`: request safe distinct values for one approved column.
   - `clarify`: ask the user a question when safe inspection is not enough.
   - `refuse`: reject unsafe requests.
4. Server validates the requested action.
5. If the action is a tool call, execute the safe tool and append its sanitized result to agent state.
6. Repeat with a strict max step count.
7. Stream each validated step to the UI.

Suggested max step count for v1: 3 to 5.

## Tool Set

Start with a very small tool surface.

### `inspect_distinct`

Purpose: resolve enum-like or categorical ambiguity.

Input:

```json
{
  "table": "customers",
  "column": "jenis_kelamin",
  "reason": "Resolve mapping for requested gender filter"
}
```

Server-side validation:

- Table and column must exist in the current introspected schema.
- Column must be classified as safe for distinct inspection.
- Query must be generated by server code, not copied from the model.
- Use selected schema and dialect-aware quoting.
- Apply hard limits.

Execution shape:

```sql
SELECT <column>, COUNT(*) AS count
FROM <schema>.<table>
WHERE <column> IS NOT NULL
GROUP BY <column>
ORDER BY count DESC
LIMIT 25
```

Return to model:

```json
{
  "values": ["L", "P"],
  "valueCount": 2,
  "truncated": false
}
```

Do not return sample rows.

### Future Tools

- `inspect_column_stats`: null count, distinct count, min/max for safe non-PII columns.
- `inspect_relationships`: confirm FK-like relationships from schema metadata only.
- `explain_query`: existing query analyzer path.
- `ask_user`: structured clarification when inspection is blocked.

## Data Safety Policy

Classify columns before allowing any inspection tool.

### Always Blocked

Do not inspect distinct values for columns likely to contain PII, secrets, or free text:

- Names: `name`, `full_name`, `first_name`, `last_name`, `nama`
- Email: `email`, `mail`
- Phone: `phone`, `mobile`, `telp`, `whatsapp`
- Address/location detail: `address`, `alamat`, `street`, `lat`, `lng`
- IDs and identifiers: `nik`, `ktp`, `ssn`, `passport`, `npwp`, `tax_id`
- Credentials/secrets: `password`, `token`, `secret`, `api_key`
- Free text: `note`, `notes`, `comment`, `description`, `message`, `bio`

### Usually Allowed

Distinct inspection is allowed for low-cardinality categorical columns:

- Gender/sex fields: `gender`, `sex`, `jenis_kelamin`, `jk`
- Status fields: `status`, `state`, `stage`
- Boolean flags: `is_*`, `has_*`, `*_flag`
- Type/category fields: `type`, `category`, `kategori`, `role`
- Enumerated codes with low cardinality

### Runtime Guardrails

Even for allowed columns:

- Refuse if distinct cardinality is too high.
- Refuse if values look like emails, phone numbers, long names, addresses, tokens, or long free text.
- Return values only when they are short categorical labels or codes.
- Prefer returning counts and normalized category labels over raw values where possible.

Recommended v1 thresholds:

- Max distinct values returned: 25.
- Max raw value length returned to model: 40 characters.
- If more than 25 distinct values exist, mark `truncated: true` and ask user to clarify unless the answer is already clear.

## Streaming Design

Use a server streaming endpoint for the agent flow, separate from or replacing `/api/generate`.

Candidate route:

```text
POST /api/agent-query
```

Stream event types:

```ts
type AgentStreamEvent =
  | { type: "status"; message: string }
  | { type: "tool_call"; tool: "inspect_distinct"; table: string; column: string }
  | { type: "tool_result"; tool: "inspect_distinct"; summary: string }
  | { type: "final_sql"; sql: string; queryType: QueryType }
  | { type: "clarify"; question: string }
  | { type: "error"; error: string };
```

The UI should render these events as an activity timeline. The final SQL then feeds the existing `processSQL` flow so pagination, mutation safety, DDL confirmation, sorting, and analysis continue to work.

## API Design

### Existing Flow

```text
PromptInput -> /api/generate -> processSQL -> /api/query or /api/mutate
```

### Target v1 Flow

```text
PromptInput -> /api/agent-query streaming
             -> final_sql event
             -> existing processSQL
             -> /api/query or /api/mutate
```

This keeps the execution safety logic mostly unchanged.

## Implementation Phases

### Phase 1: Foundations

- Add shared agent event types.
- Add column safety classifier.
- Add dialect-aware safe `inspectDistinctValues` helper.
- Add tests for column classification and generated inspection SQL.

### Phase 2: Agent API

- Add `/api/agent-query` streaming route.
- Define structured model response schema for next actions.
- Validate every model-requested action server-side.
- Add max-step and timeout limits.
- Return `final_sql` into existing query flow.

### Phase 3: UI Streaming

- Add agent activity state to `app/page.tsx`.
- Render a compact activity timeline near the SQL/result area.
- Handle `clarify` events without running SQL.
- Preserve current loading, error, pagination, mutation, and DDL behavior.

### Phase 4: Guardrail Hardening

- Add pattern-based PII detection for returned distinct values.
- Add cardinality checks before returning values to the model.
- Add audit logging for tool calls without storing sensitive values.
- Add tests for blocked PII columns and allowed categorical columns.

### Phase 5: Expand Tooling

- Add more read-only metadata tools only after `inspect_distinct` is proven safe.
- Consider relationship inspection and safe aggregate stats.
- Avoid any tool that returns arbitrary rows.

## Open Questions

- Should users be able to disable agentic inspection and keep one-shot generation?
- Should safe distinct values be shown to the user in the timeline, or only summarized?
- Should blocked inspection trigger a clarification question or a refusal?
- Should column safety classification be configurable per project/database?
- How should MySQL schema qualification differ from PostgreSQL schema selection in tool queries?

## Acceptance Criteria for v1

- Ambiguous categorical prompts can trigger safe distinct inspection before SQL generation.
- Distinct inspection cannot run against obvious PII or free-text columns.
- The model never receives arbitrary row data.
- User sees a streaming activity timeline.
- Final SQL remains visible and goes through existing execution safety gates.
- Existing non-agent query behavior can remain available as a fallback.
